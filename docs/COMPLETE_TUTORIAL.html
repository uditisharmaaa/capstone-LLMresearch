Part 1: Foundations - What is Machine Learning?

Traditional Programming vs Machine Learning

In traditional programming, you write explicit rules:

# Traditional: You tell the computer exactly what to do
def is_spam(email):
    if "FREE MONEY" in email:
        return True
    if "Nigerian prince" in email:
        return True
    return False

In machine learning, you give examples and the computer learns the rules:

# ML: You give examples, computer figures out the pattern
spam_emails = ["FREE MONEY NOW", "You won lottery", ...]
not_spam = ["Meeting tomorrow", "Project update", ...]

model = train(spam_emails, not_spam)  # Computer learns patterns
model.predict("Congratulations you won!")  # → "spam" (it figured this out)
Think of teaching a child to recognize dogs. You don't explain "4 legs, fur, tail, barks" - you just show them many pictures of dogs and many pictures of not-dogs. Eventually, they learn to recognize dogs they've never seen before. That's machine learning.

The Three Types of Machine Learning

1. Supervised Learning (What we use)

You have labeled data - you know the right answers.

Example: 100 emails labeled "spam" or "not spam". Train on these, predict new emails.

In our project: We'll have code labeled "AI-generated" or "human-written".

2. Unsupervised Learning (Also used in our project)

No labels - just find patterns in the data.

Example: Group customers into segments based on behavior.

In our project: Clustering code to see if AI code naturally groups separately from human code.

3. Reinforcement Learning (Not used here)

Learn by trial and error with rewards/punishments.

Example: AI learning to play chess by playing millions of games.

Key Vocabulary

Model
The "thing" that learns patterns. Like a brain that gets trained.
Training
The process of showing examples to the model so it learns patterns.
Features
The measurable properties we extract from data. Like "email length" or "number of exclamation marks".
Labels
The answers we're trying to predict. Like "spam" or "AI-generated".
Prediction
Using a trained model to guess labels for new data.
"What type of machine learning does your project use?"

Answer: "We use both supervised and unsupervised learning. For clustering and similarity analysis, we use unsupervised learning to see if AI code naturally groups together. When we train a classifier to predict AI vs human, that's supervised learning because we have labeled examples."

Part 2: How Computers "Read" Text and Code

The Fundamental Problem

Computers only understand numbers. They can't read "Hello World" - they need it converted to numbers first.

Imagine you need to compare two essays, but you're only allowed to use numbers. How would you do it? You might count words, measure sentence length, count punctuation, etc. That's essentially what we do with code.

Step 1: Tokenization

Tokenization means splitting text into smaller pieces called "tokens".

# Original code
def calculate_sum(a, b):
    return a + b

# After tokenization (one approach)
["def", "calculate_sum", "(", "a", ",", "b", ")", ":", "return", "a", "+", "b"]

Different tokenization strategies:

  • Word tokenization: Split on spaces and punctuation
  • Subword tokenization: Split words into pieces ("calculate" → "calc", "ulate")
  • Character tokenization: Every character is a token

Step 2: Converting Tokens to Numbers

Method 1: One-Hot Encoding

Give each unique token a position, mark 1 for present, 0 for absent.

Vocabulary: [def, return, if, for, while, print]
              Position:  0     1     2   3    4      5

"def" → [1, 0, 0, 0, 0, 0]
"return" → [0, 1, 0, 0, 0, 0]
"if" → [0, 0, 1, 0, 0, 0]

Problem: Vectors are huge (vocabulary can be 50,000+ words) and don't capture meaning ("happy" and "joyful" are completely different vectors).

Method 2: Bag of Words

Count how many times each word appears.

Code: "for i in range(10): print(i)"

Vocabulary: [for, i, in, range, print, 10]
Count:      [1,   2, 1,  1,     1,     1]

Problem: Loses word order. "Dog bites man" = "Man bites dog".

Method 3: TF-IDF (What we use)

Weight words by importance. Common words get low weight, rare words get high weight.

We'll explain this in detail in Part 3.

Method 4: Embeddings (What CodeBERT uses)

Learn a dense vector (like 768 numbers) that captures meaning.

We'll explain this in Part 6.

"How do you convert code to something a computer can analyze?"

Answer: "We use multiple approaches. First, we tokenize the code - split it into individual tokens like keywords, variable names, and operators. Then we convert these tokens to numerical representations. We use TF-IDF to create vectors based on token importance, and CodeBERT to create semantic embeddings that capture the meaning of the code."

Part 3: TF-IDF - Your First ML Technique

What Does TF-IDF Stand For?

TF = Term Frequency (how often a word appears in THIS document)

IDF = Inverse Document Frequency (how rare the word is OVERALL)

The Intuition

Some words are more "informative" than others:

  • The word the appears everywhere → Not informative
  • The word enumerate appears in some Python code → Somewhat informative
  • The word pygame appears rarely → Very informative (tells you it's a game!)

TF-IDF gives high scores to words that are frequent in this document but rare overall.

The Math: Step by Step

Step 1: Calculate Term Frequency (TF)

How often does this word appear in this specific document?

TF(word, document) = (times word appears in document) / (total words in document)

Example:

Document: "for i in range(10): for j in range(5): print(i, j)"

Word "for" appears: 2 times
Total words: 12

TF("for", document) = 2/12 = 0.167

Step 2: Calculate Inverse Document Frequency (IDF)

How rare is this word across ALL documents?

IDF(word) = log(total documents / documents containing word)

Example:

Total documents: 100
Documents containing "for": 95 (very common!)
Documents containing "enumerate": 15 (less common)

IDF("for") = log(100/95) = log(1.05) = 0.02  (low - not distinctive)
IDF("enumerate") = log(100/15) = log(6.67) = 0.82  (higher - more distinctive)

Step 3: Multiply TF × IDF

TF-IDF(word, document) = TF(word, document) × IDF(word)

Result:

  • Words frequent in THIS doc but rare overall → HIGH score
  • Words common everywhere → LOW score
  • Words rare in this doc → LOW score

Complete Worked Example

We have 3 code files:
Doc1: "def add(a, b): return a + b"
Doc2: "def subtract(a, b): return a - b"
Doc3: "for i in range(10): print(i)"

Vocabulary: [def, add, subtract, return, for, range, print, a, b, i]

Step 1: Term Frequency for Doc1
- "def": 1/8 = 0.125
- "add": 1/8 = 0.125
- "return": 1/8 = 0.125
- "a": 2/8 = 0.250
- "b": 2/8 = 0.250
- others: 0

Step 2: IDF across all docs
- "def": appears in 2/3 docs → IDF = log(3/2) = 0.18
- "add": appears in 1/3 docs → IDF = log(3/1) = 0.48  ← More distinctive!
- "return": appears in 2/3 docs → IDF = log(3/2) = 0.18
- "a": appears in 2/3 docs → IDF = log(3/2) = 0.18
- "for": appears in 1/3 docs → IDF = log(3/1) = 0.48

Step 3: TF-IDF for Doc1
- "def": 0.125 × 0.18 = 0.023
- "add": 0.125 × 0.48 = 0.060  ← Highest! Most distinctive word for Doc1
- "return": 0.125 × 0.18 = 0.023

Doc1 vector: [0.023, 0.060, 0, 0.023, 0, 0, 0, 0.045, 0.045, 0]

Why We Use TF-IDF for Code

  • Different AI models might prefer different keywords
  • Coding style affects word choice (e.g., list comprehensions vs loops)
  • It's fast and interpretable (we can see which words matter)

Part 4: Vectors and Similarity

What is a Vector?

A vector is just a list of numbers. That's it.

A vector: [0.5, 0.3, 0.8, 0.1]

You can think of it as:
- A point in space (4-dimensional in this case)
- An arrow from the origin to that point
- A list of measurements/features
Think of describing a person with numbers: [height_cm, weight_kg, age_years] = [175, 70, 25]. That's a 3D vector representing a person. Similar people have similar vectors.

Why Vectors Matter for Us

We convert each code file into a vector:

  • TF-IDF gives us a 500-number vector (500 word features)
  • CodeBERT gives us a 768-number vector (learned features)

Now we can mathematically compare code files by comparing their vectors!

Measuring Similarity: Three Approaches

Approach 1: Euclidean Distance

The straight-line distance between two points.

distance = √[(x₁-x₂)² + (y₁-y₂)² + ...] 
Point A = [1, 2]
Point B = [4, 6]

Distance = √[(1-4)² + (2-6)²]
         = √[9 + 16]
         = √25 = 5

Problem: Affected by magnitude. A long document has larger values, making it seem "far" from a short document even if they're similar in content.

Approach 2: Cosine Similarity (What we use)

Measures the angle between two vectors, ignoring their length.

cosine_similarity = (A · B) / (|A| × |B|)

Where:

  • A · B (dot product) = multiply corresponding elements and sum them
  • |A| (magnitude) = √(sum of squared elements)
Vector A = [1, 2, 3]
Vector B = [2, 4, 6]

Dot product: (1×2) + (2×4) + (3×6) = 2 + 8 + 18 = 28

Magnitude of A: √(1² + 2² + 3²) = √14 ≈ 3.74
Magnitude of B: √(2² + 4² + 6²) = √56 ≈ 7.48

Cosine similarity = 28 / (3.74 × 7.48) = 28/28 = 1.0

Result: 1.0 means identical direction (B is just 2×A)

Interpretation:

  • 1.0 = Identical (same direction)
  • 0.0 = Unrelated (perpendicular)
  • -1.0 = Opposite

Why we use it: Document length doesn't matter - we only care about the "direction" of the content.

Approach 3: Edit Distance (Levenshtein)

Counts the minimum edits needed to transform one string into another.

"cat" → "car" = 1 edit (substitute t→r)
"cat" → "cart" = 1 edit (insert r)
"cat" → "dog" = 3 edits (change all 3 letters)
"kitten" → "sitting" = 3 edits

For code, we compare the entire code as a string.

Why we use it: The Hoq & Leinonen paper used edit distance, so we compute it for comparison.

Similarity Matrix

We compute similarity between EVERY pair of code files:

100 code files → 100×100 similarity matrix

        File1  File2  File3  ...  File100
File1   1.00   0.85   0.72  ...   0.68
File2   0.85   1.00   0.79  ...   0.71
File3   0.72   0.79   1.00  ...   0.83
...
File100 0.68   0.71   0.83  ...   1.00

- Diagonal is always 1.0 (file compared to itself)
- Matrix is symmetric (similarity A→B = similarity B→A)

In Our Code

File: src/similarity/analysis.py

"Why cosine similarity instead of Euclidean distance?"

Answer: "Cosine similarity is more appropriate for text and code analysis because it measures the angle between vectors rather than the magnitude. This means a 50-line code file and a 100-line code file can still have high similarity if they use similar words in similar proportions. Euclidean distance would penalize them for being different lengths, even if the content is similar."

Part 5: Abstract Syntax Trees (AST)

The Problem with Text-Based Analysis

Looking at code as text has limitations:

# These two functions do the EXACT same thing:

# Version 1
def add(a, b):
    return a + b

# Version 2
def sum_numbers(x, y):
    result = x + y
    return result

# As text, they look different (different names, different structure)
# But structurally and semantically, they're identical!

We need a way to analyze code structure, not just text.

What is an Abstract Syntax Tree?

An AST is a tree representation of code that captures its grammatical structure.

Remember sentence diagrams from English class? "The cat sat on the mat" becomes a tree with Subject, Verb, Object branches. AST does the same for code. 
# Code
if x > 0:
    return x
else:
    return -x

# AST (simplified)
         If Statement
        /     |      \
   Condition  Body   Else-Body
      |        |        |
   Compare   Return   Return
   /  |  \     |        |
  x   >   0    x      UnaryOp
                       /   \
                      -     x

Why "Abstract"?

It removes irrelevant details:

  • Whitespace and indentation → Gone
  • Comments → Gone
  • Variable names → Kept as "Name" nodes, but could be normalized
  • Parentheses for grouping → Structure captured, parens removed

How Python's AST Module Works

import ast

code = """
def greet(name):
    print("Hello, " + name)
"""

tree = ast.parse(code)
print(ast.dump(tree, indent=2))

# Output:
Module(
  body=[
    FunctionDef(
      name='greet',
      args=arguments(args=[arg(arg='name')]),
      body=[
        Expr(
          value=Call(
            func=Name(id='print'),
            args=[
              BinOp(
                left=Constant(value='Hello, '),
                op=Add(),
                right=Name(id='name')
              )
            ]
          )
        )
      ]
    )
  ]
)

AST Node Types We Track

Node Type What It Represents Example
FunctionDef Function definition def foo():
If If statement if x > 0:
For For loop for i in range(10):
While While loop while True:
Return Return statement return x
Call Function call print("hi")
BinOp Binary operation a + b
Compare Comparison x > 0
ListComp List comprehension [x*2 for x in lst]

Features We Extract from AST

1. Tree Depth

How deeply nested is the code? More nesting = deeper tree.

# Shallow (depth ~3)
def add(a, b):
    return a + b

# Deep (depth ~6)
def complex():
    for i in range(10):
        if i > 5:
            for j in range(i):
                if j % 2 == 0:
                    print(j)

Why it matters: AI tends to write flatter code than beginners.

2. Node Type Distribution

Count of each node type: How many If statements? How many For loops?

Why it matters: Different models have preferences (e.g., list comprehensions vs loops).

3. Cyclomatic Complexity

Number of independent paths through the code.

Complexity = 1 + (# of if) + (# of for) + (# of while) + (# of except) + ... 
# Complexity = 1 (single path)
def simple():
    return 42

# Complexity = 3 (three paths: x>0, x==0, x<0)
def classify(x):
    if x > 0:
        return "positive"
    elif x == 0:
        return "zero"
    else:
        return "negative"

Why it matters: Measures code complexity independent of length.

4. Control Flow Pattern

A string encoding the sequence of control structures:

Code:
def game():
    for move in moves:        # [
        if valid(move):       # ?
            apply(move)
            if won():         # ?
                return True   # R
    return False              # R

Pattern: "F[?[?R]]R"

F = Function
[ ] = For loop
? = If statement
R = Return

Why it matters: Captures structural patterns at a high level.

Answer: "AST analysis captures the structural patterns of code regardless of superficial differences like variable names, whitespace, or comments. Two functionally identical programs with different variable names will have very similar AST structures. This is important because students might rename variables in AI-generated code to hide its origin, but the structural patterns remain detectable."

Part 6: Neural Networks and CodeBERT

What is a Neural Network?

A neural network is a computer system loosely inspired by the human brain. It consists of:

  • Neurons: Simple units that take inputs, multiply by weights, and produce output
  • Layers: Groups of neurons
  • Connections: Weighted links between neurons
Think of it like a factory assembly line. Raw materials (inputs) enter, pass through multiple stations (layers) where workers (neurons) process them, and a finished product (output) comes out. During training, we adjust how each worker does their job (weights) to make better products.

A Single Neuron

Inputs: [x1, x2, x3] = [0.5, 0.8, 0.2]
Weights: [w1, w2, w3] = [0.4, 0.3, 0.6]
Bias: b = 0.1

Step 1: Weighted sum
z = (x1×w1) + (x2×w2) + (x3×w3) + b
z = (0.5×0.4) + (0.8×0.3) + (0.2×0.6) + 0.1
z = 0.2 + 0.24 + 0.12 + 0.1 = 0.66

Step 2: Activation function (e.g., ReLU)
output = max(0, z) = max(0, 0.66) = 0.66

What is a Transformer?

The Transformer is a neural network architecture that revolutionized NLP. Key innovations:

Self-Attention

Every word can "look at" every other word to understand context.

Sentence: "The cat sat on the mat because it was tired"

Question: What does "it" refer to?

Self-attention lets "it" look at all other words:
- "it" looks at "cat" → high attention (likely reference)
- "it" looks at "mat" → low attention
- "it" looks at "sat" → low attention

Result: Model understands "it" = "cat"

What is BERT?

BERT = Bidirectional Encoder Representations from Transformers

  • Developed by Google in 2018
  • Pre-trained on massive amounts of text (Wikipedia, books)
  • Learns general language understanding
  • Can be fine-tuned for specific tasks

What is CodeBERT?

CodeBERT = BERT adapted for code

  • Developed by Microsoft Research
  • Pre-trained on code AND documentation (6 programming languages)
  • Understands both natural language and code

How CodeBERT Works (Simplified)

1

Tokenization

Split code into tokens (subwords).

"def calculate_sum" → ["def", "calculate", "_", "sum"]
2

Initial Embedding

Each token gets an initial vector (768 numbers).

"def" → [0.12, -0.45, 0.33, ..., 0.78]  (768 numbers)
"calculate" → [0.08, 0.22, -0.15, ..., 0.41]
3

12 Transformer Layers

Each layer uses self-attention. After each layer, the embeddings become more "contextual" - they incorporate information from surrounding tokens.

After Layer 1: "def" embedding knows it's followed by "calculate"
After Layer 6: "def" embedding understands it's a function definition
After Layer 12: "def" embedding captures full context of the function
4

Pooling

Average all token embeddings to get ONE vector for the entire code.

Token embeddings: [[...], [...], [...], ...]  (N tokens × 768)
Mean pooling: [...]  (1 × 768)

This single 768-number vector represents the entire code's meaning.

Why 768 Numbers?

768 is the "hidden size" - a design choice that balances:

  • Enough dimensions to capture complex patterns
  • Not so many that computation becomes too slow

Each number represents some abstract "feature" learned during training. We can't easily interpret individual numbers, but the overall vector captures semantic meaning.

What Makes CodeBERT Special

  • Bimodal: Trained on code + natural language descriptions together
  • Multi-lingual: Understands Python, Java, JavaScript, PHP, Ruby, Go
  • Pre-trained: Already knows programming concepts; we just use it

In Our Code

File: src/features/semantic.py

from transformers import AutoTokenizer, AutoModel
import torch

# Load pre-trained CodeBERT
model = AutoModel.from_pretrained("microsoft/codebert-base")
tokenizer = AutoTokenizer.from_pretrained("microsoft/codebert-base")

def get_embedding(code):
    # Tokenize
    inputs = tokenizer(code, return_tensors="pt", truncation=True, max_length=512)

    # Get embeddings from model
    with torch.no_grad():  # Don't compute gradients (we're not training)
        outputs = model(**inputs)

    # Mean pooling: average all token embeddings
    embedding = outputs.last_hidden_state.mean(dim=1)

    return embedding.numpy()  # Shape: (1, 768)
"Why use CodeBERT instead of just TF-IDF?"

Answer: "TF-IDF only captures lexical patterns - which words appear and how often. It doesn't understand meaning. For example, 'def add(a, b): return a+b' and 'def sum(x, y): return x+y' would have low TF-IDF similarity because they use different words, but CodeBERT recognizes they're semantically identical - both are addition functions. CodeBERT captures semantic meaning that TF-IDF misses."

"How is CodeBERT different from GPT?"

Answer: "Both use the Transformer architecture, but they're designed for different tasks. GPT is a generative model - it predicts the next token to generate text. CodeBERT is an encoder model - it creates representations (embeddings) that capture meaning. We don't use CodeBERT to generate anything; we use it to convert code into vectors we can compare."

Part 7: Statistics You Need to Know

Why Statistics?

When we find that AI code has higher similarity than human code, we need to ask: Is this a real pattern or just random chance?

Statistics answers this question rigorously.

Basic Concepts

Mean (Average)

Sum of all values divided by count.

Values: [0.75, 0.82, 0.79, 0.88, 0.76]
Mean = (0.75 + 0.82 + 0.79 + 0.88 + 0.76) / 5 = 4.0 / 5 = 0.80

Standard Deviation (Std Dev)

How spread out are the values? Low std dev = values are close together.

Values: [0.75, 0.82, 0.79, 0.88, 0.76], Mean = 0.80

Step 1: Differences from mean
[0.75-0.80, 0.82-0.80, 0.79-0.80, 0.88-0.80, 0.76-0.80]
= [-0.05, 0.02, -0.01, 0.08, -0.04]

Step 2: Square them
[0.0025, 0.0004, 0.0001, 0.0064, 0.0016]

Step 3: Average of squares (variance)
= 0.011 / 5 = 0.0022

Step 4: Square root (standard deviation)
= √0.0022 = 0.047

Interpretation: Most values are within ±0.047 of the mean.

Hypothesis Testing

A formal framework for deciding if observed differences are real.

The Null Hypothesis (H₀)

The "boring" assumption: there's no real difference, any observed difference is just random noise.

Example: "AI code and human code have the same similarity patterns."

The Alternative Hypothesis (H₁)

What we're trying to prove: there IS a real difference.

Example: "AI code has different similarity patterns than human code."

p-value

The probability of seeing this result (or more extreme) IF the null hypothesis were true.

p-value = 0.03 means:
"If there were NO real difference, there's only a 3% chance
we'd see data this extreme by random chance."

Since 3% is pretty unlikely, we reject the null hypothesis
and conclude there IS a real difference.

Thresholds:

  • p < 0.05: Significant (less than 5% chance it's random)
  • p < 0.01: Very significant
  • p < 0.001: Highly significant

Our result: p = 1.38e-93 = 0.000...000138 (93 zeros!)

This is essentially zero - there's virtually no chance our results are random.

Mann-Whitney U Test

We use this test because it doesn't assume data follows a "bell curve" (normal distribution).

How It Works (Simplified)

Group A (AI similarities): [0.85, 0.88, 0.82, 0.90]
Group B (Human similarities): [0.72, 0.68, 0.75, 0.70]

Step 1: Combine and rank all values
All values sorted: 0.68, 0.70, 0.72, 0.75, 0.82, 0.85, 0.88, 0.90
Ranks:              1     2     3     4     5     6     7     8

Step 2: Sum ranks for each group
Group A (AI) ranks: 5 + 6 + 7 + 8 = 26
Group B (Human) ranks: 1 + 2 + 3 + 4 = 10

Step 3: Compare
If groups were the same, we'd expect similar rank sums.
Group A has much higher ranks → They're different!

Step 4: Calculate p-value
(Mathematical formula determines probability of this occurring by chance)

Effect Size: Cohen's d

p-value tells us IF there's a difference. Cohen's d tells us HOW BIG the difference is.

Cohen's d = (Mean₁ - Mean₂) / Pooled Standard Deviation 
Group A: Mean = 0.86, Std = 0.03
Group B: Mean = 0.71, Std = 0.03

Pooled Std = √[(0.03² + 0.03²) / 2] = 0.03

Cohen's d = (0.86 - 0.71) / 0.03 = 0.15 / 0.03 = 5.0

This is a HUGE effect (d > 0.8 is "large")

Interpretation guidelines:

Cohen's d Interpretation
0.2 Small effect (noticeable if you look carefully)
0.5 Medium effect (clearly noticeable)
0.8+ Large effect (obvious difference)

Test Result What It Means

Claude vs GPT-4o Mini Cohen's d = 0.81, p < 0.001 Large, highly significant difference
GPT-4o vs GPT-4o Mini Cohen's d = 0.49, p < 0.001 Medium, highly significant difference
Bottom line: All three AI models produce statistically distinguishable code patterns. This isn't random - the differences are real and substantial.
"What does your p-value of 1.38e-93 actually mean?"

Answer: "It means if there were truly no difference between within-model and between-model similarities, the probability of observing data this extreme by random chance is essentially zero - about 1 in 10^93. For context, there are only about 10^80 atoms in the observable universe. This gives us extremely high confidence that the patterns we're seeing are real, not statistical noise."

"Why use Mann-Whitney instead of a t-test?"

Answer: "The t-test assumes data follows a normal (bell-curve) distribution. Similarity scores often don't follow this distribution - they tend to cluster near 1.0 for similar code. Mann-Whitney is a non-parametric test that makes no assumptions about the distribution, making it more robust for our data."

Part 8: Classification Models (Future Work)

We haven't trained classifiers yet (waiting for human code), but here's what we'll use:

Random Forest

Imagine asking 100 people for directions. Each person gives slightly different advice based on different landmarks they notice. You take a vote and go with the majority. That's Random Forest - many simple decision trees "voting" together.

What is a Decision Tree?

Is code length > 100 lines?
├── YES: Is function_count > 5?
│        ├── YES: Predict "AI"
│        └── NO: Is has_list_comprehension?
│                ├── YES: Predict "AI"
│                └── NO: Predict "Human"
└── NO: Is has_docstrings?
        ├── YES: Predict "AI"
        └── NO: Predict "Human"

Why "Forest"?

One tree can overfit (memorize training data). Many trees averaging together are more robust.

Why "Random"?

  • Each tree sees a random subset of training data
  • Each tree considers a random subset of features

This diversity makes the ensemble stronger.

XGBoost

XGBoost = eXtreme Gradient Boosting

Like Random Forest, but trees are built sequentially, each one correcting the mistakes of the previous ones.

Imagine a student taking a test. After grading, a tutor focuses on the questions they got wrong. Then another tutor focuses on remaining mistakes. Each tutor "boosts" performance on weak areas.

Why we'll use it: Often wins machine learning competitions, very effective for tabular data (like our features).

Evaluation Metrics We'll Use

Metric Formula What It Measures
Accuracy (Correct predictions) / (Total) Overall correctness
Precision TP / (TP + FP) When we say "AI", how often are we right?
Recall TP / (TP + FN) Of all actual AI code, how much do we catch?
F1-Score 2 × (P × R) / (P + R) Balance of precision and recall

Where: TP = True Positive, FP = False Positive, FN = False Negative

Important trade-off: In academic integrity, false positives (accusing innocent students) are VERY costly. We'll prioritize high precision even if it means lower recall.

Part 10: Defending Your Work - Q&A Prep

Questions About the Approach

"Why did you choose similarity analysis over direct classification?"

Answer: "Direct classification gives binary yes/no answers, which can be problematic for academic integrity - false accusations are very costly. Our similarity-based approach provides probability scores and shows which AI-generated examples the submission is most similar to. This is more transparent, allows instructors to make informed judgments, and can adapt to new AI models without retraining."

"How is this different from existing plagiarism detectors like MOSS?"

Answer: "MOSS compares submissions against each other and a database of known sources. It fails for AI code because each generation is unique - MOSS only catches 1% of AI pairs. We're detecting patterns that are consistent across AI generations, not looking for direct copying."

"What if students modify the AI-generated code?"

Answer: "This is a great question we're investigating. Our multi-feature approach helps - even if students change variable names (defeating TF-IDF), the AST structure and CodeBERT semantic embedding may still capture AI patterns. The Hoq paper found that asking AI to 'write like a beginner' only reduced similarity by 15-20%, suggesting structural patterns persist."

Questions About the Data

"Why only 100 samples?"

Answer: "This is our initial dataset for developing the methodology. 100 samples across 3 models gives us enough data to establish that model fingerprints exist (which we've confirmed statistically). We'll expand to more samples and more assignments once we validate the approach with human code."

"Why Connect4 specifically?"

Answer: "Connect4 is a realistic CS1/CS2 assignment that requires multiple programming concepts: 2D arrays, loops, functions, win detection algorithms. Prior work (Hoq) used very simple 10-line problems focused on conditionals. We wanted to test whether patterns persist in more complex, realistic assignments."

Questions About Results

"What's your main finding so far?"

Answer: "Our main finding is that different AI models produce statistically distinguishable code patterns. Claude produces the most consistent code (0.883 within-model similarity), while GPT-4o produces the most varied (0.785). All pairwise model comparisons are highly significant (p < 0.001) with medium to large effect sizes. This suggests AI code detection is feasible and might even allow model attribution."

"Your within-model vs between-model comparison shows negative Cohen's d. Doesn't that mean your hypothesis failed?"

Answer: "For TF-IDF, the difference is very small (d = -0.038) and the groups overlap substantially. However, when we look at individual model comparisons, we see large effects. The key insight is that each model has its own fingerprint - Claude code is more similar to other Claude code than to GPT code. For CodeBERT embeddings, we do see positive separation (d = 0.57) with extreme significance (p = 1.38e-93)."

Questions About Limitations

"What are the limitations of your approach?"

Answer: "Several limitations: (1) We don't have human code yet to test our main hypothesis. (2) We only tested one assignment type. (3) AI models evolve - patterns might change with new versions. (4) Sophisticated students might combine human and AI code. (5) Some human code might naturally resemble AI patterns, risking false positives. We're addressing these in future work."

"What's the biggest threat to validity?"

Answer: "The biggest threat is generalization. We've shown patterns exist for Connect4 with current models, but we need to verify this holds across different assignments, different programming languages, future AI models, and importantly, that human code is sufficiently different. That's why getting the pre-ChatGPT student submissions is critical."

Questions About Next Steps

"What's your plan once you get the human code?"

Answer: "Three main analyses: (1) Test if AI code clusters separately from human code using the same similarity measures. (2) Train a classifier (Random Forest, XGBoost) and evaluate accuracy, precision, recall. (3) Visualize the combined clustering to understand the decision boundary. The key metric is precision - we want to minimize false accusations."
